# 1교시 **NumPy 기초 — 벡터 연산·브로드캐스팅**

## 1. 도입: 왜 NumPy인가? (예제 1-1 설명)

- **초보자 눈높이 비유**:
    - 파이썬 기본 리스트로 1만 개 데이터에 연산(`[r / 1023 * 3.3 for r in raws_list]`)을 하면, 파이썬이 하나씩 상자를 열어 계산하느라 시간이 걸립니다.
    - NumPy 배열(`big / 1023 * 3.3`)은 데이터들을 메모리에 딱 붙여두고 C 언어 엔진이 한 번에 통째로 계산합니다.
    - 하나의 배열에는 오직 한 가지 데이터 타입(dtype)만 들어갈 수 있어 이런 고속 연산이 가능합니다.
- **💡 파이썬 리스트가 NumPy보다 훨씬 느린 3가지 결정적 이유**
    
    #### **1. 메모리 구조: '주소 포인터 모음' vs '연속된 데이터 덩어리' (메모리 파편화)**
    
    - **파이썬 리스트 (포인터 배열) :**
        - 리스트는 실제 숫자를 들고 있는 것이 아니라, 메모리(RAM) 여기저기 흩어져 있는 **객체들의 '주소(포인터)'만 상자에 모아둔 형태**입니다.
        - 계산할 때마다 매번 주소를 찾아 메모리의 다른 위치로 이동해야 하므로 캐시 미스(Cache Miss)가 빈번하게 발생하여 속도가 느립니다.
    - **NumPy 배열 (`ndarray`) :**
        - C 언어의 배열처럼 **실제 숫자 데이터들이 메모리에 빈틈없이 연속으로(Contiguous Memory)** 딱 붙어 저장됩니다.
        - CPU가 데이터를 한 번에 통째로 캐시 메모리에 적재(Cache Locality)할 수 있어 읽는 속도가 압도적으로 빠릅니다.
    
    #### **2. 타입 검사(Type Checking): '매번 상자 열어보기' vs '단일 타입 보장'**
    
    - **파이썬 리스트 (다양한 타입 허용) :**
        - 리스트는 `[1, "문자", 3.14]`처럼 서로 다른 타입의 값을 섞어 담을 수 있습니다.
        - 유연하지만, 덧셈이나 곱셈을 할 때마다 파이썬 인터프리터가 "이번에 꺼낸 게 정수인가? 문자인가?"를 원소마다 일일이 확인(동적 타입 검증 및 언박싱)해야 해서 계산 시간의 대부분을 낭비합니다.
    - **NumPy 배열 (단일 타입 고정 - `dtype`) :**
        - 배열을 만들 때 `dtype=int64`처럼 **모든 칸의 타입을 오직 하나로 고정**합니다.
        - "모든 칸이 똑같은 숫자"라는 것이 100% 보장되므로, 타입 검사를 완전히 생략하고 곧바로 계산에 돌입합니다.
    
    #### **3. 실행 주체: '파이썬 인터프리터의 한 줄 반복' vs 'C 언어 엔진 & SIMD'**
    
    - **파이썬 리스트 (`for` 반복문) :**
        - 파이썬 인터프리터가 원소를 1개씩 꺼내면서 반복문(`for`) 코드를 한 줄씩 해석하고 실행합니다.
    - **NumPy 배열 (벡터화 연산 - Vectorization) :**
        - 반복문을 파이썬이 돌지 않고, 내부의 **고도로 최적화된 C/C++ 및 포트란 컴파일 엔진**에 한 번에 넘겨 처리합니다.
        - 최신 CPU의 **SIMD(Single Instruction Multiple Data)** 기술을 활용해, CPU 명령어 하나로 **여러 개의 숫자를 병렬로 동시에 계산**합니다.
    - **한줄 요약** :
        - NumPy가 리스트보다 빠르다.

## 2. 기본 개념: `shape`, `dtype`, `ndim` 읽기 (예제 1-2 설명)

- **핵심 메시지**: *"NumPy 배열을 만나면 값부터 보지 말고 생김새(Shape)부터 확인하자!"*
- **속성 풀이**:
    - `a = np.array([512, 723, 1023])`
        - `shape`: `(3,)` $\rightarrow$ 1차원이며 원소가 3개 있음. shape는 튜플 형태로 반환함
        - `dtype`: `int64` $\rightarrow$ 정수형 데이터. 하나의 배열에는 오직 하나의 데이터 타입 가능
        - `ndim`: `1` $\rightarrow$ 1차원 배열.
    - `M = np.arange(12).reshape(3, 4)`
        - **`np.arange(12)`** : 0부터 11까지 연속된 숫자 12개를 한 줄로 만듭니다.
        - **`.reshape(3, 4)`** : 그 12개 숫자를 3행 4열(가로 4칸씩 3줄) 모양으로 다시 배치합니다.
            - 그냥 (12, )이었던게 (3, 4)로 변한것.
        - 0부터 11까지 12개 숫자를 3행 4열로 재배열한 2차원 표 형태(`shape: (3, 4)`, `ndim: 2`).

## **3. 벡터 연산: 같은 기호, 완전히 다른 동작 (예제 1-3 설명)**

- **초보자 눈높이 비유 :**
    - **파이썬 리스트 :** 데이터가 든 상자들이 기차처럼 연결된 구조라, 무언가를 계산하려면 사람이 일일이 상자를 하나씩 열어보며 작업해야 합니다.
    - **NumPy 배열(벡터) :** 데이터 전체를 하나의 덩어리(벡터)로 취급합니다. 한 번 명령을 내리면 데이터 전체의 모든 칸에 동시에 계산이 적용됩니다.
- **핵심 비교 : `2`의 동작 차이**
    - **리스트 `[1, 2] * 2`** $\rightarrow$ **`[1, 2, 1, 2]` (이어 붙이기)**
        - 파이썬 기본 리스트의 곱셈은 "문자열 반복"처럼 덩어리를 그대로 복사해 길이를 늘립니다.
    - **배열 `np.array([1, 2]) * 2`** $\rightarrow$ **`[2, 4]` (원소별 곱셈, Element-wise)**
        - 배열 안의 알맹이 숫자들(`1`과 `2`) 각각에 `2`를 곱해 새로운 값으로 바꿉니다.
- **반복문(`for`) 없는 일괄 계산 :**
    - **예제 코드 :** `volts = np.round(RAWS / 1023 * 3.3, 2)`
    - **동작 원리 :** 센서에서 들어온 원시값 수만 개가 든 `RAWS` 배열 전체에 나눗셈(`/ 1023`)과 곱셈(`3.3`)을 한 번에 명령합니다.
    - **효과 :** `for r in raws_list:` 같은 복잡한 반복문이나 컴프리헨션 없이 수식 한 줄로 데이터 전체를 변환합니다.
    - 리스트에서 이와 같은 연산을 하려면 원소를 하나하나 꺼내서 작업해야했지만, 넘파이에서는 np.array를 마치 하나의 원소처럼 이용해 작업이 가능.
- **비교 연산도 배열 전체로 한 번에 :**
    - **예제 코드 :**
        
        ```python
        temps = np.array([24.1, 36.9, 28.3, 35.4])
        print(temps > 35)  # [False,  True, False,  True]
        ```
        
    - **동작 원리 :** `35`보다 큰지 묻는 조건문(`> 35`) 역시 모든 원소에 동시에 적용되어 각 칸마다 `True`/`False`로 구성된 **불리언(Boolean) 배열**을 돌려줍니다.
    - **연계 :** 이 결과는 2교시에서 조건에 맞는 데이터만 쏙 골라내는 '불리언 마스크'의 핵심 재료로 쓰입니다.
- **한 줄 요약 :**
    - 리스트 연산은 상자 늘리기, NumPy 벡터 연산은 모든 데이터 알맹이에 연산자를 동시에 적용하는 방식입니다.

## 4. 브로드캐스팅(Broadcasting): 크기가 달라도 계산되는 규칙 (예제 1-4 설명)

- **원리 설명**:
    - 모양이 다른 두 배열을 더할 때, 차원이 맞는 쪽으로 작은 배열이 자동으로 '복사되어 늘어나듯' 채워져 계산됩니다.
    - `(2, 3)` 행렬 + `(3,)` 벡터 $\rightarrow$ 벡터가 아래로 한 줄 더 복사되어 늘어난 뒤 더해짐.
- **주의할 점 (`ValueError`)**:
    - `(3,)` 배열과 `(4,)` 배열을 더하면 모양을 맞출 수 없어 `operands could not be broadcast together with shapes (3,) (4,)` 에러가 발생합니다.
    - **팁**: 에러 메시지가 뜨면 놀라지 말고 적혀 있는 두 `shape`의 숫자를 비교하도록 안내합니다.
- **초보자 눈높이 비유 :**
    - 두 배열의 크기(`shape`)가 다를 때, **작은 쪽 배열을 복사기나 도장처럼 쾅쾅 찍어서 큰 쪽 배열의 크기와 똑같이 복사해 늘린 뒤** 계산하는 기능입니다.
- **차원이 늘어나는 원리 설명 :**
    - 모양이 다른 두 배열을 계산할 때, NumPy는 "오른쪽(마지막 축) 끝"부터 줄을 맞춥니다.
    - **1단계 (차원 수 맞추기) :** 차원이 부족한 `(3,)` 벡터의 **왼쪽(앞자리)에 `1`을 자동으로 채워 넣어 `(1, 3)` 행렬**로 차원을 승격시킵니다.
        - `(3,)` $\rightarrow$ `(1, 3)`
    - **2단계 (자리별 비교) :**
        
        ```
        행렬 A:  (2,  3)
        벡터 B:  (1,  3)  <-- 앞자리에 1이 채워진 상태
        ----------------
        비교:    1->2  3==3  (열 크기 3은 딱 맞고, 행 크기 1은 2로 늘어남!)
        ```
        
    - **3단계 (복사 및 연산) :** `(1, 3)` 행렬의 행이 아래로 한 줄 더 복사되어 `(2, 3)` 모양이 된 뒤 행렬과 1:1로 더해집니다.
- **브로드캐스팅 동작 단계별 예시 :**
    1. **스칼라(숫자 하나)와 배열 :**
        - `[10, 20, 30] + 5`
        - 차원이 없는 숫자 `5`가 `[5, 5, 5]`로 스스로 크기를 불려서 각각 더해집니다 $\rightarrow$ 결과: `[15, 25, 35]`
    2. **2차원 행렬 `(2, 3)` + 1차원 벡터 `(3,)` :**
        - 행렬 `[[10, 20, 30], [40, 50, 60]]` 아래에 `[1, 2, 3]`을 더하는 경우
        - `[1, 2, 3]`이 아래로 한 줄 더 복사되어 똑같은 2행 모양 `[[1, 2, 3], [1, 2, 3]]`이 된 뒤 1:1로 더해집니다 $\rightarrow$ 결과 `shape: (2, 3)`
    3. **열 벡터 `(3, 1)` + 행 벡터 `(1, 4)` :**
        - 세로로 길쭉한 3줄과 가로로 길쭉한 4칸을 더하면,
        - 각각 가로·세로로 도장 찍듯 복사되어 바둑판 모양 `(3, 4)` 행렬로 커집니다.
- **핵심 판별 규칙 ("오른쪽 끝자리 맞추기") :**
    - **비교 방법 :** 두 배열의 `shape`을 **오른쪽(뒤쪽) 끝**을 기준으로 세로 줄을 맞춰 적습니다. (자릿수가 비는 앞쪽은 자동으로 1로 취급)
    - **합격 조건 :** 줄을 맞춘 모든 자리에서 "완전히 같거나, 다르면 둘 중 하나가 무조건 1"이어야 합니다.
- **판별 예시 비교 :**
    - **가능한 경우 (O) :**
        - `(2, 3)`과 `(3,)` $\rightarrow$ 뒤쪽 자리가 `3 vs 3`으로 **완전히 같음** (비어있는 앞자리는 1로 취급되어 1 vs 2로 통과)
        - `(4, 1)`과 `(4, 3)` $\rightarrow$ 뒤쪽 자리가 `1 vs 3`으로 **한쪽이 1임**, 앞자리는 `4 vs 4`로 같음
        - `(3, 1)`과 `(1, 4)` $\rightarrow$ 뒤쪽(`1 vs 4`), 앞쪽(`3 vs 1`) 모두 **한쪽이 1임**
    - **불가능한 경우 (X) — `ValueError` 발생 :**
        - `(3,)`과 `(4,)` $\rightarrow$ 뒤쪽 자리가 `3 vs 4`로 서로 다르고 **둘 다 1이 아님** $\rightarrow$ 계산 불가!
        - `(2, 6)`과 `(1, 3)` $\rightarrow$ 뒤쪽 자리가 `6 vs 3`으로 서로 다르고 **둘 다 1이 아님** (3의 배수여도 불가능, 무조건 1만 늘어남) $\rightarrow$ 계산 불가!

# **2교시 · NumPy 활용 — 마스크·통계·이미지=배열**

## **1. 슬라이스는 뷰(View): 참조 모델의 재림 (예제 2-1 설명)**

- **초보자 눈높이 비유 :**
    - 파이썬 리스트 슬라이싱(`a[2:5]`)은 독립된 '복사본'을 만듭니다.
    - NumPy 슬라이싱은 복사가 아니라 원본을 그대로 들여다보는 '투명 창문(View/참조)'입니다.
- **차원 무관 원칙 (1차원 / 2차원 모두 동일) :**
    - 1차원이든 2차원(`M[:2, 1:3]`)이든 콜론(`:`)으로 자른 모든 슬라이스는 차원과 상관없이 무조건 원본 메모리를 공유하는 뷰(View)입니다.
    - 잘라낸 조각의 값을 수정하면 원본 행렬의 값도 즉시 함께 변경됩니다.
- **코드 포인트 :**
    - `b = a[2:5]` 후 `b[0] = 999`로 바꾸면 원본 `a`의 값도 `999`로 바뀝니다.
    - 원본을 지키면서 독립된 사본을 만들려면 반드시 `.copy()`를 써야 합니다 (`c = a[2:5].copy()`).
    - NumPy의 `.copy()`는 기본적으로 메모리 공간을 새로 분리하는 완전한 독립 사본(Deep Copy)을 만듭니다.
- **한 줄 요약 :**
    - 1차원이든 다차원이든 슬라이싱은 무조건 원본 공유(View)이며, 원본과 인연을 끊으려면 `.copy()`(Deep Copy)를 써야 합니다.

- **`groupby` 내부 동작 3단계 :**

## **1. enumerate와 zip: 인덱스 번호와 묶음 순회 졸업 (예제 5-1 설명)**

## **2. 이터레이터(Iterator): 딱 한 번만 흘러가는 강물 (예제 5-2 설명)**

- **초보자 눈높이 비유 :**
    - 리스트는 책장에 꽂힌 책이라 원할 때마다 몇 번이고 다시 읽을 수 있습니다.
    - 이터레이터는 '한 번 컵에 따라 마시면 바닥나는 자판기 음료(또는 흐르는 강물)'입니다.
- **사전 지식: `map(함수, 리스트)`이란?**
    - 리스트 안에 있는 데이터들을 하나씩 꺼내어 지정한 함수를 적용해 주는 내장 도구입니다.
    - 예: `m = map(str, [1, 2])` $\rightarrow$ 숫자 `1`과 `2`를 각각 문자열 `'1'`, `'2'`로 **변환할 준비만 해둔 이터레이터 객체**를 만듭니다.
    - *(중요)* `map`은 그 자리에서 변환 결과를 통째로 다 만들어두는 것이 아니라, "요청이 들어올 때마다 하나씩 **변환해서 건네줄 준비**"만 하고 기다립니다.

### **💡 '변환해서 건넬 준비만 한다'는 게 무슨 뜻일까?**

- **디스크 버퍼 비유 (핵심 개념) :**
    - **일반 리스트 변환 (`[str(x) for x in [1, 2]]`) :**
        - 100만 개짜리 파일 전체를 한꺼번에 메모리(RAM)에 몽땅 적재해 두는 방식입니다. (RAM이 꽉 차서 터질 수 있음)
    - **이터레이터 `map(str, [1, 2])` :**
        - 아직 아무 일도 하지 않고, 단지 "디스크의 몇 번째 줄을 가리키는 손가락(포인터/커서)"과 "str 함수라는 도구"만 쥐고 있는 상태입니다.
- **실제 내부에서 일어나는 일 (어떻게 변환하는가?) :**
    1. `m = map(str, [1, 2])`를 실행했을 때:
        - 숫자 `1`이나 `2`를 글자로 바꾸는 작업은 **단 1개도 실행되지 않았습니다.**
        - 파이썬은 단지 **"첫 번째 원소 위치를 가리키는 화살표"** 와 **"str(문자열 변환) 함수"** 레시피만 머릿속에 기억해 둡니다.
    2. 누군가 **"다음 거 내놔(`next(m)`)"** 하고 벨을 눌렀을 때 비로소:
        - 화살표가 가리키는 `1`을 꺼냅니다.
        - 들고 있던 `str` 함수에 통과시켜 `'1'`로 즉석 변환합니다.
        - 완성된 `'1'`을 바깥으로 툭 던져주고, 화살표를 다음 칸인 `2`로 옮겨놓은 뒤 **작업을 일시 정지**합니다.
- **왜 `list(m)`을 두 번 쓰면 다음엔 텅 비어있을까? :**
    
    ```python
    m = map(str, [1, 2])
    print(list(m))  # ['1', '2'] 출력 (데이터를 끝까지 다 뽑아냄)
    print(list(m))  # [] 빈 리스트 출력 (남은 데이터가 없음!)
    ```
    
    - `list(m)`은 파이썬이 뒤에서 `next(m)` 벨을 **끝까지 연타**하는 명령입니다.
    - 첫 번째 `list(m)` 때 화살표(포인터)가 맨 끝까지 이동하면서 모든 숫자를 즉석 변환해 바깥으로 넘겨버렸기 때문에,
    - 포인터가 이미 끝에 도달한 상태에서 다시 `list(m)`을 부르면 **더 이상 읽어올 다음 데이터(EOF)가 없어서 빈 껍데기 `[]`가 반환**되는 것입니다.
    - **원리 :**
        1. 첫 번째 `list(m)`을 실행하는 순간, 파이썬은 이터레이터 `m`에게 **"다음 거 줘!"** 를 반복해서 요청합니다.
        2. `1`을 꺼내고, `2`를 꺼내어 리스트에 담는 순간 **자판기 내부 통(이터레이터)이 완전히 텅 비게 됩니다.**
        3. 따라서 두 번째 `list(m)`을 호출했을 때는 이미 커서(포인터)가 맨 끝에 도달해 있으므로, **더 이상 꺼내줄 데이터가 없어 빈 리스트 `[]`가 반환** 됩니다.
- **왜 이런 귀찮은 방식을 쓸까?**
    - 데이터를 미리 한꺼번에 수백만 개 만들어 메모리에 쌓아두지 않고, **필요한 순간에만 하나씩 변환하고 버리기 때문에 메모리를 거의 쓰지 않기 때문**입니다.
- **한 줄 요약 :**
    - `map`은 필요할 때마다 뽑아주는 이터레이터이며, `list()`로 한 번에 끝까지 털어내면 내부 데이터가 모두 소모되어 두 번째부터는 텅 비어버립니다.

## **3. 제너레이터(Generator): `yield`로 만드는 자판기 (예제 5-3 설명)**

- **초보자 눈높이 비유 :**
    - **일반 함수(`return`) :** 붕어빵 1,000개를 한꺼번에 다 구워서 큰 상자(리스트)에 담아 손님에게 한 번에 건네줍니다. (상자가 너무 커서 메모리가 터질 수 있음)
    - **제너레이터(`yield`) :** 붕어빵 자판기입니다. 손님이 버튼(`next()`)을 누를 때마다 **딱 1개만 구워서 내놓고(`yield`), 다음 주문이 올 때까지 그 자리에서 일시 정지**합니다.
- **`return` vs `yield`의 차이 :**
    - `return` : 값을 돌려주고 **함수를 완전히 끝내버림** (메모리 정리).
    - `yield` : 값을 바깥으로 건네주고 현재 실행 상태(변수, 위치) 그대로 '일시정지'해 둠. 다음 요청이 오면 그 멈췄던 자리부터 이어서 실행!
- **코드 포인트 (`read_frames`) :**
    - `def read_frames(path):` 안에 `yield parse_frame(line)`이 들어가는 순간, 이 함수는 제너레이터가 됩니다.
    - `frames = read_frames(...)`를 호출해도 파일 전체를 읽지 않습니다 (실행 준비만 됨).
    - `next(frames)`를 부를 때 비로소 파일에서 딱 한 줄만 처리해서 건네줍니다.
- **핵심 장점 :**
    - 센서 데이터가 **100만 줄, 1GB짜리 파일이어도 리스트를 통째로 만들지 않기 때문에 메모리를 1줄 분량만 사용**합니다.
- **`function` vs `generator`의 타입 차이 (`type(f)` vs `type(f())`) :**
    - **둘 다 `def`로 정의 :** 코드 상에서는 둘 다 `def`로 만들어지므로 실행 전 함수 자체의 타입(`type(f)`)은 둘 다 똑같은 `<class 'function'>`입니다.
    - **키워드에 따른 반환 타입 차이 (`type(f())`) :**
        - **일반 함수 (`return`) :** 함수를 호출(`f()`)하면 코드가 끝까지 실행되어 결과값(예: `int`, `list` 등)을 반환합니다.
        - **제너레이터 함수 (`yield`) :** 내부에 `yield`가 들어있으면 호출(`f()`)하는 순간 코드가 즉시 돌지 않고, 자판기 본체인 **`<class 'generator'>` 객체를 반환**합니다.
    - **`frames = read_frames(...)`의 의미 :**
        - 파일 내용을 다 읽은 리스트가 담긴 것이 아니라, `frames` 변수 자체가 제너레이터 객체(`<class 'generator'>`)가 된 것입니다.
        - 따라서 `type(frames)`를 찍으면 `<class 'generator'>`가 출력되며, `next(frames)`를 부를 때마다 한 줄씩 꺼내오게 됩니다.
- **한 줄 요약 :**
    - 함수 안에 `yield`를 쓰면 대용량 파일도 멈췄다 이어가며 한 줄씩 메모리 부담 없이 다룰 수 있습니다.

## **4. 제너레이터 표현식과 깔끔한 f-string 정렬 (예제 5-4 설명)**

- **대괄호 없는 컴프리헨션 (제너레이터 표현식) :**
    - `[t for _, t, _, _ in ...]` $\rightarrow$ 대괄호를 쓰면 리스트를 만들어 메모리를 씁니다.
    - `sum(t for _, t, _, _ in ...)` $\rightarrow$ **대괄호를 빼면 제너레이터가 되어, 리스트 상자를 만들지 않고 즉석에서 하나씩 꺼내며 합산**합니다.
- **f-string 깔끔한 보고서 출력 팁 :**
    - `f"{'ESP32-01':10s}{26.433:8.2f}{12:7d}"`
        - `:10s` : 문자열 자리를 10칸 확보 (왼쪽 정렬).
        - `:>8s` : 8칸 확보 후 오른쪽 정렬.
        - `:8.2f` : 숫자 8칸 폭 확보하고 소수점 둘째 자리까지 반올림.
- **한 줄 요약 :**
    - 대괄호 없는 컴프리헨션으로 메모리 없이 합계를 구하고, f-string 칸 맞춤으로 반듯한 표를 만듭니다.

### **리스트 방식 vs 제너레이터 방식 비교**

#### **1. 코드로 보는 차이 (대괄호 `[]`의 유무)**

- **방법 A : 리스트 컴프리헨션 방식 (대괄호 `[]` 사용)**
    
    ```python
    # 1. 26개(혹은 100만 개) 온도를 담을 실제 '리스트 상자'를 메모리에 전부 만듦
    t_list = [t for _, t, _, _ in read_frames("data/stream_boot.txt")]
    
    # 2. 완성된 리스트 상자를 sum()에 넘겨서 합산 후 평균 계산
    avg = sum(t_list) / 26
    print(round(avg, 2))  # 26.43
    ```
    
- **방법 B : 제너레이터 표현식 방식 (대괄호 없이 `sum()` 안에 바로 넣음)**
    
    ```python
    
      # 리스트 상자를 만들지 않고, 온도가 1개씩 나올 때마다 즉석에서 sum()에 던져서 누적
      avg = sum(t for _, t, _, _ in read_frames("data/stream_boot.txt")) / 26
      print(round(avg, 2))  # 26.43
    ```
    

#### **2. 눈에 보이는 핵심 차이 3가지**

| **비교 항목** | **방법 A: 리스트 컴프리헨션 ([...])   IPYNB** | **방법 B: 제너레이터 표현식 ((...))   IPYNB** |
| --- | --- | --- |
| **코드 형태** | 바깥쪽에 대괄호 `[ ... ]`가 감싸고 있음    | 대괄호 없이 소괄호 `sum( ... )`만 감싸고 있음    |
| **메모리(RAM) 상태** | 모든 온도를 담은 거대한 리스트 상자를 **통째로 메모리에 적재** | 리스트 상자가 아예 없음. 온도가 나오자마자 **즉석 합산하고 소멸** | 
| **데이터가 100만 줄일 때** | 100만 개짜리 숫자 리스트가 메모리를 차지함 $\rightarrow$ **메모리 낭비 위험** | 데이터를 딱 1개씩만 거쳐가므로 $\rightarrow$ **메모리 사용량 사실상 0MB (초경량)** |
| **데이터 재사용** | `t_list` 변수에 저장되어 있으므로 **언제든 다시 꺼내 쓸 수 있음** | `sum()`을 돌면서 이미 데이터를 끝까지 소모해 버려 **재사용 불가** |
